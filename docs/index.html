COMPUTE(7) · OPERATOR & API MANUAL · LINUX / KVM

Self-Hosted Firecracker MicroVM Sandboxes

Compute runs hardware-isolated Firecracker microVMs and distributed worker pools on Linux hosts with /dev/kvm. A single computed control plane serves the REST/WebSocket APIs, real-time /api/v1/ws UI sync, and embedded Web Dashboard on :18080, while remote compute-worker nodes connect outbound with zero inbound ports required.

01

Architecture & Binaries

The system consists of three Go binaries with no external orchestrator, etcd cluster, or cloud control plane required. Control-plane state lives in a single SQLite database (compute.db) alongside ext4 disk images and snapshots under COMPUTE_DATA_DIR (default /var/lib/compute inside containers, ./data on the host).

computed Control Plane

Manages users, scoped API keys, microVM lifecycle, scheduler placement, live migration, TAP/NAT/DNS/edge, and the embedded Web UI on :18080.

compute CLI & UI

Client CLI for sandboxes, SSH, streaming exec, scp file transfers, templates, workers, pools, jobs, and optional standalone compute gui mode.

compute-worker Worker Agent

Outward-dialing host agent enrolled via tokens (compute worker token create); runs sandboxes and jobs over multiplexed WS RPC/TCP tunnels.

Resource Enforcement & Embedded Web UI
computed enforces hard disk ceilings, soft + hard CPU overcommit cgroup weights, and RAM hard guarantees with idle SSD auto-hibernation (auto_hibernated). Rejections return HTTP 429 Too Many Requests with a structured ResourceLimitError. Port :18080 serves both the API and the embedded Web Dashboard; compute-gui (:8080) is strictly optional and disabled by default.
02

Host Setup, Images & Boot

Requires Linux (x86_64 or arm64), read/write /dev/kvm, unified cgroup v2 hierarchy, and at least 10 GB of free disk space. Firecracker and Jailer are bundled inside the daemon container; the container runs privileged in the host network namespace to manage mft3br0 and guest TAP interfaces.

1. start with zero-config auto-bootstrap (loopback :18080 API + embedded UI, admin / admin)
docker compose up -d
curl -fsS http://127.0.0.1:18080/api/v1/ready | python3 -m json.tool
2. optional preflight, .env customization, and host image builds
./scripts/preflight.sh
sudo ./scripts/host-prepare.sh
cp .env.example .env && chmod 600 .env
# Only required if switching COMPUTE_IMAGES_MODE=build or prebuilt:
make build-images          # builds vmlinux + ubuntu-24.04.ext4 into ./data/images
1. download and install pre-built compute CLI (Linux x86_64 / arm64)
curl -fsSL https://github.com/Rashid2G/compute/releases/latest/download/compute_1.0.0_linux_amd64.tar.gz | sudo tar -xz -C /usr/local/bin
compute --version
2. download complete suite or verify SHA-256 checksums
# Download full suite (compute, computed, compute-worker, compute-bench)
curl -fsSLO https://github.com/Rashid2G/compute/releases/latest/download/compute-suite_1.0.0_linux_amd64.tar.gz
curl -fsSLO https://github.com/Rashid2G/compute/releases/latest/download/checksums.txt
sha256sum --check --ignore-missing checksums.txt
build web bundle + Go binaries (Go 1.26+, Node 20+)
cd web && npm ci && cd ..
make build-ui              # embeds Web UI assets into computed & compute gui
make build                 # outputs compute, computed, compute-worker, compute-bench in ./bin/
make build-images
COMPUTE_ADMIN_PASSWORD=dev-only-secret ./bin/computed
COMPUTE_IMAGES_MODE: auto vs. build / prebuilt
COMPUTE_IMAGES_MODE=auto (the default) automatically downloads vmlinux, builds ubuntu-24.04.ext4, and generates the SSH key inside compute-init. Switching to build or prebuilt requires building or placing vmlinux and ubuntu-24.04.ext4 under ./data/images first (make build-images or scripts/build-kernel.sh + scripts/build-rootfs.sh); otherwise startup fails with missing vmlinux.

/api/v1/health checks process liveness; /api/v1/ready inspects KVM, Firecracker binary, base kernel/rootfs, internal Ed25519 SSH key, SQLite DB, cgroup v2, and mft3br0 bridge usability (also exposed via compute doctor). Open the full Web Dashboard at http://<host>:18080/ — the standalone compute-gui container (:8080, --profile gui) is strictly optional.

03

Authentication & Configuration Precedence

Configuration resolves across four layers (lowest to highest priority): internal/config.DefaultConfig → optional JSON file (--config or /etc/compute/daemon.json) → COMPUTE_* environment variables → CLI flags.

Non-Loopback Bind Credentials (COMPUTE_BIND_ADDRESS=0.0.0.0)
Setting COMPUTE_BIND_ADDRESS=0.0.0.0 (or any non-loopback IP) without setting a non-default COMPUTE_ADMIN_PASSWORD (or explicitly clearing COMPUTE_ADMIN_PASSWORD= and setting COMPUTE_ADMIN_SECRET) in .env causes computed to refuse startup. If binding a specific non-loopback IP (e.g. 10.0.0.5), also set COMPUTE_HEALTHCHECK_HOST=10.0.0.5.
.env snippet for non-loopback / LAN / Tailscale exposure
COMPUTE_BIND_ADDRESS=0.0.0.0
COMPUTE_ADMIN_PASSWORD=replace-with-openssl-rand-base64-32
# Or use a static admin secret instead of a seeded password:
# COMPUTE_ADMIN_PASSWORD=
# COMPUTE_ADMIN_SECRET=replace-with-openssl-rand-base64-32
# If binding a specific IP (e.g. 10.0.0.5), match healthcheck host:
# COMPUTE_HEALTHCHECK_HOST=10.0.0.5
Variable Default Behavior
COMPUTE_LISTEN 127.0.0.1:18080 Full listen address; overrides COMPUTE_BIND_ADDRESS and COMPUTE_API_PORT.
COMPUTE_HEALTHCHECK_HOST 127.0.0.1 Host probed by Compose healthcheck; set to COMPUTE_BIND_ADDRESS when binding a specific non-loopback IP.
COMPUTE_AUTH_ENABLED true Enforces session cookie (compute_session) or Authorization: Bearer cmp_... on API/WS/UI routes.
COMPUTE_SIGNUP_ENABLED false When false, POST /api/v1/auth/signup returns 403 signup_disabled and registration is hidden in the UI.
COMPUTE_ADMIN_USERNAME admin Bootstrap admin username synced at startup (companion: COMPUTE_ADMIN_EMAIL=admin@compute.local).
COMPUTE_ADMIN_PASSWORD admin (loopback only) Admin password synced on boot; must be rotated or cleared (COMPUTE_ADMIN_PASSWORD=) on non-loopback binds.
COMPUTE_ADMIN_SECRET — Optional static bearer secret resolving directly to the bootstrap admin identity.
COMPUTE_DATA_DIR /var/lib/compute Root directory for SQLite DB (data/compute.db), base images (images/), and VM disks (vms/).
COMPUTE_TLS_CERT_FILE — Optional PEM certificate (must be paired with COMPUTE_TLS_KEY_FILE) for native HTTPS.
04

Creating, Operating & Bulk Managing Sandboxes

Each sandbox allocates an ext4 root volume copied from a base image (default ubuntu-24, 50 GiB sparse), a MAC/IP lease on mft3br0, a dedicated TAP interface (mftap-*), and an interactive SSH/exec target. Pin placement to a specific pool or node using pool_id / worker_id in POST /api/v1/vms or the Web UI (the scheduler selects automatically otherwise). Bulk lifecycle operations run concurrently in a single request via POST /api/v1/vms/bulk-create, POST /api/v1/vms/bulk-clone, POST /api/v1/vms/bulk-delete, and POST /api/v1/vms/bulk-action (start, stop, restart, save-state, resume, protect, unprotect, delete). Send "async": true to queue the work on the daemon: it returns 202 with a task_id and keeps running even if the browser refreshes or disconnects. Poll GET /api/v1/tasks/{id} for the final per-item outcome. Requests are capped at 100 items and rejected with 429 when the backend queue is saturated.

sandbox lifecycle, streaming exec, file copy, and single-request bulk actions
# Provision and start a 2 vCPU / 2048 MiB sandbox with real CLI flags
compute sandbox create --name dev-api --vcpus 2 --memory 2048 --disk 20480 --image ubuntu-24 --start

# Interactive shell or streamed command execution
compute sandbox ssh dev-api
compute sandbox exec dev-api -- uname -a

# Copy local directory tree into guest /workspace and publish it over HTTP ingress
compute scp -r ./my-service dev-api:/workspace/
compute expose dev-api 3000        # -> http://dev-api-3000.localhost:18080/ (loopback default)
compute ports dev-api
compute unexpose dev-api 3000

# Single-request bulk stop across multiple sandboxes (synchronous by default)
curl -fsS -X POST http://127.0.0.1:18080/api/v1/vms/bulk-action \
  -H "Authorization: Bearer $COMPUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"ids":["dev-api","staging-box"],"action":"stop"}'

# Queue 10 sandboxes for durable creation; work survives a refresh/disconnect
curl -fsS -X POST http://127.0.0.1:18080/api/v1/vms/bulk-create \
  -H "Authorization: Bearer $COMPUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"async":true,"items":[{"name":"worker-1","vcpus":2,"memory_mb":2048,"auto_start":true}]}'

# Resolve the queued task: queued | completed | partial | failed
curl -fsS http://127.0.0.1:18080/api/v1/tasks/task_1a2b3c4d \
  -H "Authorization: Bearer $COMPUTE_API_KEY"
05

Replicating (Cloning) Sandboxes

Cloning duplicates a sandbox's disk image and metadata into independent microVMs with optional CPU, memory, disk size, and network isolation overrides.

  • Web UI: Use Replicate on any sandbox row or Inspector toolbar to create 1–5 numbered replicas (<base>-1 .. <base>-N) with per-tier overrides and optional auto-start.
  • REST API: Invoke POST /api/v1/vms/{id}/clone (see REST API below).
clone with resource & isolation overrides via REST API
curl -fsS -X POST http://127.0.0.1:18080/api/v1/vms/dev-api/clone \
  -H "Authorization: Bearer $COMPUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "dev-api-canary",
    "vcpus": 4,
    "memory_mb": 4096,
    "disk_gb": 30,
    "network_isolated": true,
    "auto_start": true
  }'
06

Pausing, Resuming & Idle SSD Auto-Hibernation

save-state checkpoints a running Firecracker microVM via the Firecracker snapshot API, writing exact vCPU registers, virtio device state, and guest RAM pages (vm.snap + vm.mem) to SSD before stopping the VMM process. Host CPU and RAM capacity return to the scheduler while the sandbox state changes to paused (PAUSED (STATE SAVED) in the Web UI).

When idle_ram_snapshot_enabled=true (default), the control plane also automatically snapshots idle non-protected sandboxes to SSD after idle_threshold_seconds (default 900s) — or earlier under memory pressure when auto_reclaim_on_pressure=true — marking them auto_hibernated=true so active workloads keep guaranteed RAM.

serialize live guest state to SSD and resume
compute sandbox save-state dev-api
compute sandbox resume dev-api
07

Snapshots & Reusable Templates

Disk templates freeze a sandbox's ext4 root filesystem as a named template so subsequent sandboxes boot with compilers, toolchains, or dependencies already installed on disk.

create a reusable disk template and launch a sandbox from it
# Snapshot sandbox disk into a named template
compute template create rust-toolchain --vm dev-api --desc "Rust 1.85 + cargo cache"

# Provision and start a new sandbox from that template
compute template launch rust-toolchain --name build-runner-01 --tier 4vcpu
08

Workers, Pools & Distributed Jobs

Remote compute-worker nodes enroll over an outbound WebSocket RPC & multiplexed TCP tunnel to computed — zero inbound ports are needed on worker hosts. Control-plane SSH, file APIs, streaming exec, process control, and disk migrations tunnel back over that outbound session.

Pool precedence on enrollment: token.pool_id (if set on the token) → worker --pool / COMPUTE_POOL_ID → default. Tokens created with --name pin to that worker name; unnamed tokens bind to the first worker that enrolls and allow seamless reconnects across restarts.

enroll a remote worker into a pool and dispatch a distributed job
# 1. Mint an enrollment token on the control plane
compute worker token create --name gpu-node-01 --pool gpu-pool

# 2. Start compute-worker on the remote KVM host (zero inbound firewall ports needed)
compute-worker run \
  --control-plane http://<control-plane-host>:18080 \
  --token <printed-token> \
  --name gpu-node-01 \
  --pool gpu-pool \
  --max-vcpus 16 --max-memory-mb 32768 --max-disk-mb 204800

# 3. Dispatch an ephemeral job with workspace sync and live log streaming
compute job run --image ubuntu-24 --pool gpu-pool --files ./ --cwd /workspace -- go test ./...
09

Load Balancing, Resource Limits & Live Migration

The cluster scheduler places sandboxes and jobs across ready workers (plus the local control-plane node nod_host_local) using configurable placement policies, per-node allocation caps, strict resource enforcement, and live sandbox/pool migration. The embedded Web Dashboard maintains a persistent /api/v1/ws WebSocket connection for real-time cluster sync.

Mechanism / Policy Behavior & Endpoints
Node Allocation Limits PATCH /api/v1/workers/{id} updates allocated_vcpus, allocated_mem_mb, allocated_disk_mb, pool_id, labels, and status (ready, cordoned, draining, offline) immediately.
Load Balancer Strategies GET/PUT /api/v1/scheduler/policy configures strategy: least_loaded (weighted CPU/RAM/Disk headroom), round_robin, bin_pack (fullest fit first), or spread (fewest running VMs).
CPU Soft + Hard Overcommit cpu_soft_overcommit_ratio (1.5) & cpu_hard_overcommit_ratio (2.0): full cgroup CPU weight below soft ratio, proportional weight scaling between soft & hard, hard rejection above ceiling.
RAM Hard Guarantee + Idle SSD memory_hard_guarantee=true forbids RAM overcommit; idle non-protected VMs auto-snapshot to SSD (auto_hibernated=true) via idle_threshold_seconds / auto_reclaim_on_pressure.
Disk Hard-Limit-Only & HTTP 429 disk_hard_enforcement=true enforces allocated_disk_mb, host_reserved_disk_mb (2048 MB), and free disk. Any disk/RAM/CPU hard limit breach returns HTTP 429 ResourceLimitError (RESOURCE_LIMIT_EXCEEDED).
Sandbox & Pool Migration POST /api/v1/vms/{id}/migrate streams chunked gzipped disk + snapshot/mem state to target_worker_id or target_pool_id (force: true stops & restarts running VMs). POST /api/v1/pools/{id}/migrate moves workers and capacity-preflighted sandboxes.
Persistent /api/v1/ws Sync Single RBAC-scoped WebSocket pushes immediate snapshots on connect and cluster mutations across sandboxes, workers, pools, templates, images, port forwards, and events.
configure scheduler policy, cap node resources, and migrate a sandbox
# Switch cluster load balancer to spread with 1.5x soft / 2.0x hard CPU overcommit
curl -fsS -X PUT http://127.0.0.1:18080/api/v1/scheduler/policy \
  -H "Authorization: Bearer $COMPUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "strategy": "spread",
    "cpu_soft_overcommit_ratio": 1.5,
    "cpu_hard_overcommit_ratio": 2.0,
    "memory_hard_guarantee": true,
    "idle_ram_snapshot_enabled": true,
    "disk_hard_enforcement": true
  }'

# Cap allocation limits on a worker node
curl -fsS -X PATCH http://127.0.0.1:18080/api/v1/workers/gpu-node-01 \
  -H "Authorization: Bearer $COMPUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"allocated_vcpus": 12, "allocated_mem_mb": 24576, "allocated_disk_mb": 153600}'

# Migrate a sandbox to another worker or pool
curl -fsS -X POST http://127.0.0.1:18080/api/v1/vms/dev-api/migrate \
  -H "Authorization: Bearer $COMPUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"target_pool_id": "gpu-pool", "force": true}'

Serving Apps at Their Own Origin

Every published guest port gets a dedicated origin instead of a path prefix. The app sees / as its root, so redirects, history.pushState, absolute asset imports, cookies and service workers behave exactly as they do when the app runs locally. No HTML or JavaScript rewriting is involved.

publish a port and inspect its origin
# Public: anyone with the URL can reach the app
compute expose web 8080
# -> http://web-8080.localhost:18080/            (loopback daemon, no DNS needed)

# Private: owning tenant session or short-lived token
compute expose web 8080 --private

# Preferred label (made globally unique)
compute expose web 8080 --subdomain my-app

compute ports web
compute unexpose web 8080
ModeURL shapeSelected when
Subdomain https://<slug>.<serve-domain>/ COMPUTE_SERVE_DOMAIN is set, or the API binds loopback (domain defaults to localhost). Requires a wildcard DNS record and wildcard certificate for public domains.
Port https://<daemon-host>:<serve-port>/ COMPUTE_PUBLIC_URL points at a non-loopback host, or the API binds a non-loopback address without a serve domain. Listeners are allocated from COMPUTE_SERVE_PORT_START..COMPUTE_SERVE_PORT_END.
Wildcard DNS + TLS for public subdomains
Point *.serves.example.com at the daemon and set COMPUTE_SERVE_DOMAIN=serves.example.com. Terminate TLS either at the daemon (COMPUTE_SERVE_TLS_CERT_FILE / COMPUTE_SERVE_TLS_KEY_FILE) or in front of it (Caddy/nginx wildcard). For a tailnet or bare public IP, use port mode: map each allocated port with tailscale serve --bg --tcp=<port> tcp://127.0.0.1:<port> (tailnet-only HTTP) or --https=8443 (Tailscale can terminate HTTPS only on 443/8443/10000). Port-mode URLs use http:// unless COMPUTE_SERVE_TLS_* is configured.

Access control. A public exposure bypasses tenant authentication. A private exposure accepts the daemon session/bearer credentials, or a short-lived HMAC token minted by POST /api/v1/sandboxes/<id>/serve-token. Browsers are bounced through GET /api/v1/serve/authorize, which exchanges the daemon session for a compute_serve cookie scoped to the serve origin. Tokens are signed with COMPUTE_SERVE_TOKEN_KEY (or a key derived from COMPUTE_ADMIN_SECRET).

EnvironmentDefaultBehavior
COMPUTE_PUBLIC_URL—Externally reachable daemon base URL used in port-mode serve URLs and advertised on /api/v1/version.
COMPUTE_SERVE_DOMAIN—Enables subdomain mode: <slug>.<serve-domain>.
COMPUTE_SERVE_BIND127.0.0.1Bind address for port-mode listeners; use 0.0.0.0 for direct public exposure.
COMPUTE_SERVE_PORT_START / _END18400 / 18500Inclusive port range for port-mode serve listeners.
COMPUTE_SERVE_TLS_CERT_FILE / _KEY_FILE—Optional TLS for port-mode listeners (falls back to the API listener's certificate).
COMPUTE_SERVE_TOKEN_KEY—HMAC key for private-serve tokens. Empty derives from COMPUTE_ADMIN_SECRET, else a random per-process key.
Port mode and cookies
Distinct ports are distinct origins for storage, service workers and CORS, but browsers scope cookies by host, not port. Use subdomain mode when apps must not share cookies. Apps that hard-code an absolute base URL at build time still need their own base-URL configuration.
11

Networking, DNS & SSH Routing

By default (COMPUTE_NETWORK_MODE=nat), computed creates Linux bridge mft3br0 (172.16.0.1/16, subnet 172.16.0.0/16), attaches per-sandbox TAP interfaces (mftap-*), and configures masquerade/forwarding rules without modifying the host's default route.

Mode / Mechanism Behavior
network_isolation=account Default. Sandboxes belonging to the same account can reach one another across mft3br0.
network_isolation=isolated Installs per-TAP iptables isolation dropping east-west traffic to sibling sandboxes while retaining gateway egress.
DNS Responder (:53) When COMPUTE_DNS_ENABLED=true and COMPUTE_DNS_BASE_DOMAIN (or COMPUTE_DOMAIN in Compose) is set, resolves <sandbox>.<user>.<zone> (tailnet IP first, guest IP fallback) plus apex/api/gui/www.
HTTP Edge (:80) & Port Exposures Routes wildcard hostnames to sandboxes. Published ports use their own origin (subdomain or dedicated port) instead of a shared path prefix; see Serving Apps, docs/dns-ssh.md and docs/domain-options.md.

REST & WebSocket API Reference (/api/v1)

Control-plane routes serve JSON under /api/v1. Authenticate using the compute_session HttpOnly cookie or Authorization: Bearer cmp_.... Both /api/v1/vms/* and /api/v1/sandboxes/* address sandboxes.

Method Path Behavior
GET /api/v1/health · /api/v1/ready Public liveness probe (health) and full KVM/Firecracker/image/bridge readiness report (ready).
GET / POST /api/v1/auth/status · /api/v1/auth/login Query auth/signup policy; exchange credentials for session cookie and bearer token.
POST /api/v1/auth/signup Self-register when COMPUTE_SIGNUP_ENABLED=true; otherwise returns 403 signup_disabled.
GET / POST / DELETE /api/v1/users · /api/v1/users/{id} Admin-only user listing, provisioning, and deletion (protects bootstrap admin and caller).
GET / POST / PATCH / DELETE /api/v1/vms · /api/v1/vms/{id} List, create (optional pool_id / worker_id placement), inspect, patch, or delete microVM sandboxes (returns HTTP 429 ResourceLimitError if node limits exceeded).
POST /api/v1/vms/{id}/run · /stop · /exec Boot microVM, stop microVM, or execute shell command synchronously via SSH.
POST /api/v1/vms/{id}/clone Clone sandbox disk with overrides (name, vcpus, memory_mb, disk_gb, network_isolated, auto_start).
POST /api/v1/vms/{id}/save-state · /resume Serialize running Firecracker vCPU/memory state to SSD or resume from saved state.
POST /api/v1/vms/{id}/migrate Migrate sandbox disk (and snapshot/mem if paused) to target_worker_id or target_pool_id (force: true for running VMs).
POST /api/v1/vms/bulk-create · /bulk-clone · /bulk-delete · /bulk-action Single-request bulk create, clone, delete, or lifecycle action (start, stop, restart, save-state, resume, protect, unprotect, delete). Send "async": true to queue durably and resolve via GET /api/v1/tasks/{id}.
GET / POST / DELETE /api/v1/templates · /api/v1/templates/{id} · /launch List, create from vm_id, inspect, delete, or launch new sandboxes from reusable disk templates.
GET / PATCH /api/v1/workers · /api/v1/workers/{id} List workers or update node allocated_vcpus, allocated_mem_mb, allocated_disk_mb, pool_id, labels, and status.
POST /api/v1/pools/{id}/migrate Migrate workers (migrate_workers) and/or capacity-preflighted sandboxes (migrate_sandboxes) out of a pool.
GET / PUT /api/v1/scheduler/policy Read or update cluster load balancer strategy (least_loaded, round_robin, bin_pack, spread), CPU overcommit ratios, RAM/idle SSD rules, and disk limits.
POST / DELETE /api/v1/sandboxes/{id}/expose · /ports/{port} Publish or remove a guest port. Responses include the absolute public_url for the exposure's own origin.
POST /api/v1/sandboxes/{id}/serve-token Mint a short-lived URL for a private exposure ({"guest_port":8080}).
GET /api/v1/serve/authorize Browser auth hop for private serves: exchanges the daemon session for a serve-scoped token.
WS /api/v1/ws Persistent RBAC-scoped WebSocket streaming real-time cluster state snapshots to the Web Dashboard and live clients.

TypeScript & Python SDKs

First-party SDKs in sdk/typescript and sdk/python wrap sandbox creation, commands.run, files (read/write/list/mkdir/remove), process management, and cleanup context managers.

sdk/typescript — create, write file, run command, kill
import { Sandbox } from "@compute/sdk";

const sbx = await Sandbox.create({
  host: "http://127.0.0.1:18080",
  apiKey: process.env.COMPUTE_API_KEY,
  name: "agent-runner",
  vcpus: 2,
  memoryMb: 2048,
});

await sbx.files.write("/workspace/hello.txt", "hello microvm\n");
const res = await sbx.commands.run("cat /workspace/hello.txt && uname -r");
console.log(res.stdout, res.exitCode, res.durationMs);
await sbx.kill();
sdk/python — context-managed sandbox lifecycle
import os
from compute import Sandbox

with Sandbox.create(
    host="http://127.0.0.1:18080",
    api_key=os.environ.get("COMPUTE_API_KEY"),
    name="py-runner",
    vcpus=2,
    memory_mb=2048,
) as sbx:
    sbx.files.write("/workspace/script.py", "print(6 * 7)\n")
    res = sbx.commands.run("python3 /workspace/script.py")
    print(res.stdout.strip())
